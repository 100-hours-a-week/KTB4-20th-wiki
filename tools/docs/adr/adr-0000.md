# ADR-0000: 타운홀 Issue를 GitHub Actions 예약 실행으로 주 1회 자동 게시

## Status

Accepted

1. Proposed: 2026-10-09
2. Accepted: 2026-10-10 (PR #115 머지)

## Context

**문제**

- 프로젝트 정보가 5개 레포(wiki, AI, FE, BE, CLOUD)에 흩어져 있음
- 매주 월요일 타운홀 문서를 만들려면 문서 탐색, 선별, 취합, 양식 요약을 수작업으로 해야 함 (8단계)
- 최종 목표는 "누가 무엇을 하고 다음 액션은 무엇인지"의 자동 정리이나, 긴급성 때문에 타운홀 문서부터 시작하고 현황·할 일 관리는 MVP 이후로 미룸

**조건과 규모 (확인된 사실)**

- 팀원 5명, 과정 3개(AI, 풀스택, 클라우드), 타운홀 미팅일은 매주 월요일
- 입력은 wiki 레포의 `[Troubleshooting]` Issue이며, 집계 기간은 직전 일요일 20:00 ~ 실행 일요일 20:00 KST (7일)
- 2026-09-27 ~ 2026-10-04 기간의 대상 Issue는 5건
- wiki 레포는 공개(`PUBLIC`)이므로 게시된 내용은 누구나 읽을 수 있음
- 수작업 소요 시간, Gemini 호출 비용은 수치 없음

**범위와 책임 경계**

- 범위: `[Troubleshooting]` Issue 요약과 `[Townhall] YYYY-MM-DD` Issue 1건 게시
- 범위 밖: Daily Scrum, PM/PL 미팅 등 다른 문서, 다른 레포의 Issue/PR, 현황·할 일 관리
- 게시 이후 검토와 수정은 팀이 책임짐

**가정 (확인되지 않음)**

- 조직에서 GitHub Actions 예약 실행이 허용됨 (수동 실행은 확인, `schedule` 자동 발화는 미확인)
- 팀 공용 Gemini 키가 만료되거나 한도를 넘지 않음
- 팀원 5명이 매주 게시된 Issue를 빠짐없이 검토함

## Decision

우리는 매주 일요일 20:00 KST에 GitHub Actions 예약 실행(`0 11 * * 0`)으로 지난 7일의 `[Troubleshooting]` Issue를 Gemini로 요약해, `[Townhall] YYYY-MM-DD` Issue 1건(과정별 섹션)을 **게시 전 검수 없이 자동으로 게시**한다. 검토와 수정은 게시 후 월요일 발표 전에 팀원이 과정별로 수동으로 한다.

- 별도 서버 없이 wiki 레포 안(`tools/townhall/`, `.github/workflows/townhall.yml`)에서 `GITHUB_TOKEN`과 `gh` CLI로 동작하게 하여 운영 대상을 늘리지 않는다.
- 사전 검수 대신 정규식 필터로 민감 정보를 LLM 앞단에서 `[REDACTED]` 치환하고, 같은 제목의 Issue가 있으면 새로 만들지 않는다.
- 검토를 게시 후로 두는 이유는 사전 검토를 위해 문서를 나눠 운영하는 비용이 크고, 사람이 하는 단계를 최소로 줄이는 것이 목표이기 때문이다.

## Alternative / Considered Options

### 1. 수작업 유지 (매주 월요일 직접 취합)

- (장점) 별도 도구와 외부 서비스(Gemini, Actions 예약 실행) 의존이 없음
- (단점) 5개 레포를 직접 탐색하고 취합하는 8단계 수작업이 매주 반복됨
- (소결) 수작업 부담이 목표(자동 정리)와 맞지 않아 선택하지 않음

### 2. 과정별 3건 분리 + 과정별 사전 검토 후 게시

- (장점) 각 과정이 먼저 검토한 뒤 게시하므로 오류와 민감 정보가 공개되기 전에 걸러질 수 있음
- (단점) 과정별로 Issue를 따로 운영해야 하고, 게시 전에 사람이 개입해야 해서 자동 게시의 흐름이 끊김
- (소결) 검토를 게시 후 수동으로 하기로 하여 분리의 이점이 사라졌고, 처음 설계대로 1건으로 복귀함

## Consequences

### Positive (Gain)

- 전체 프로세스가 8단계에서 3단계로 단축됨 (`PROBLEM.md` 기준 사람이 직접 하는 단계는 8개 → 1개)
- 일요일 20:00 실행 후 월요일 발표 전까지 검토 시간이 확보됨
- 별도 서버가 필요 없어 운영 대상이 늘지 않음
- 같은 제목 중복 게시가 방지되고, 실패 시 수동 재실행(`workflow_dispatch`)으로 복구 가능함

### Negative (Loss)

- 게시 전 검수가 없어 오류나 민감 정보가 공개 레포에 먼저 노출될 수 있음. 정규식 필터가 있어도 마지막 방어선은 게시 후 팀원 검토임
- 실행 실패 알림이 없어, 팀원이 일요일 20:00에 직접 Issue 존재를 확인하고 없으면 수동 재실행해야 함
- 팀원 5명의 매주 검토 이행에 의존함
- 외부 의존이 늘어남: Gemini API(키 만료, 한도), GitHub Actions 예약 실행(수 분~1시간 지연 가능)
- 공동·교차 과정 이슈가 과정별로 중복 노출됨 (실제 사례: #84와 #85)
- 요약 품질이 LLM에 의존해 유사 문장이 중복될 수 있음 (실제 사례: #97)

## Compliance / Reconsideration Conditions

**결정사항 반영 여부 검증 기준**

- [x] 자동: 단위 테스트와 CI로 동작 규칙을 검증함
- [x] 수동: 일요일 확인과 월요일 사전 검토를 사람이 수행함

**결정사항 반영 여부 측정 목록**

- [x] (자동) `Townhall Tests` 워크플로가 `tools/townhall` 변경 PR에서 단위 테스트를 실행함
- [x] (자동) `[REDACTED]` 정규식 치환이 자동 테스트(`tests/test_redaction.py`)로 검증됨
- [x] (자동) 같은 제목 중복 게시 방지가 테스트와 실제 재실행(2026-10-10)으로 확인됨
- [ ] (수동) `schedule` 트리거의 자동 발화를 첫 정규 실행(2026-10-11 20:00 KST)에서 확인함
- [ ] (수동) 일요일 20:00 KST에 팀원이 `[Townhall]` Issue 존재를 확인하고, 없으면 수동 재실행함
- [ ] (수동) 월요일 발표 전 팀원이 과정별로 게시된 Issue를 검토하고 수정함

**재검토 조건**

- `schedule` 트리거가 정규 실행에서 반복적으로 발화하지 않거나 지연이 큼 → 트리거 방식을 재검토함
- 게시된 Issue에서 민감 정보 노출이 실제로 한 번이라도 발생함 → 게시 전 검수 도입을 재검토함
- 팀원 검토가 반복적으로 이행되지 않음 → 검토 방식을 재검토함
- Gemini 키 만료나 한도 초과로 실행이 반복적으로 실패함 → 요약 방식을 재검토함
